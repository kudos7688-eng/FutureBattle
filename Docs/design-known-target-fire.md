**1. 観測表は AreaIntelView と分ける**

`AreaIntelView` は材料の参考になりますが、今回の射撃判断にはそのまま使わない方がよいです。

- 更新が試合時間で約1秒ごと。通常接触は `bVisible` のものを集め、追跡中の記憶は集めません。`BattleAreaIntel.cpp:23`、`BattleAreaIntel.cpp:40`
- 敵の観測時刻は存在しますが、設定によって記録される補助情報です。全候補の出どころ・鮮度を保証する表ではありません。`BattleAreaIntel.cpp:41`、`BattleMatch.h:486`
- 偵察報告は位置だけで、負の仮キーになります。そのキーを `CanSee(ID, TargetID)` に渡すことはできません。`BattleScoutReport.cpp:38`、`BattleMatch.h:477`
- 呼び出し時に更新されるので、歩兵側から追加で呼ぶと既存の戦略側が読む更新時刻にも影響します。`BattleAreaIntel.cpp:23`

新設する `TeamKnownTargets` は、陣営別・TargetID別に、少なくとも次を持たせます。

| 項目 | 用途 |
|---|---|
| TargetID、ObservedSquadType | 候補の識別。敵の現在の兵種を判断側で読まない |
| LastKnownPosition、ObservedAt | 最終観測位置と元の観測時刻 |
| SourceUnitID、SourceSquadID、SourceKind | 直接目撃・配信済み報告などの由来 |
| ReceivedAt、ExpiresAt | 配信と有効期限。再配信で観測時刻を延長しない |

通常距離の直接観測は軍共有表へ集約し、偵察の遠見は**既存の報告完了後**に入れます。遠見を全員の接触から無条件に吸い上げると、偵察の報告待ちを迂回します。`BattleScoutReport.cpp:2`、`BattleScoutReport.cpp:150`

表の更新は知覚結果の適用後にまとめて行い、各兵から軍全体の接触を走査させません。接触へのポインタは保持せず値をコピーします。既存の接触ポインタも次の知覚更新までしか保証されません。`BattlePerception.h:49`

**2. 値1：候補選択と射撃許可を共通化する**

提案する流れは次のとおりです。

1. 既存の小隊目標・役割目標を撃てるなら、そちらを優先。
2. 有効な OwnTarget があれば、それを優先。
3. どちらも撃てなければ軍共有表を検索。
4. 鮮度・命令・武器の交戦距離で落とし、観測位置による距離と向きで上位3件を選ぶ。
5. 順に本人の `CanSee` 相当の共通センサー判定を行う。失敗したら次へ進む。
6. 通った目標について射撃準備と弾道を確認し、通常の `Fire` を使う。

現在の通常射撃は `bVisible && !bShared` と本人の `CanSee` が必要で、OwnTarget も別途あります。ここへ新しい選択結果を追加します。共有接触を偽って `bVisible=true` にする必要はありません。`BattleLeaderRuntime.cpp:986`、`BattleLeaderRuntime.cpp:995`

共通結果は、例えば `TargetID / AimPosition / Source / bTracked / CheckedAt / RejectReason`。**目標を選べたことと、実際に弾が出たことを別に扱います。**

通常射撃と覗き射撃は、この同じ候補選択・確認関数を呼びます。ただし遮蔽側には重要な接続があります。

- `Follow` は冒頭で `StepCoverAction` を呼び、遮蔽中なら先に戻ります。`Follow` の射撃末尾だけを直しても覗きには届きません。`BattleLeaderRuntime.cpp:944`
- 遮蔽側は本人／小隊の接触が無いと、射撃前に遮蔽を取り消します。軍共有目標を使う遮蔽には専用の接触解決が必要です。`BattleCoverAction.cpp:657`
- 覗きの終了判定も元の目標に対して行われています。別候補を撃てるのに `no_line` や `blind` で戻らないよう、選択結果を先に渡します。`BattleCoverAction.cpp:689`
- 実際の射撃点へ到着してから、本人の位置・姿勢で確認します。`BattleCoverAction.cpp:725`、`BattleCoverAction.cpp:736`

値1では、**新しい遮蔽スロットや新しい覗き位置を探しません**。通常位置、または既存の覗き位置から撃てる相手を選びます。今の遮蔽に対して大きく向きの違う敵なら、隠れ位置の安全性は別途再確認します。

命令の制約は新経路でも維持します。少なくとも通常の Move、援護対象の限定、防衛範囲、区画任務の制約を共通化します。既存の `WeaponOrderAllows` が入口の候補です。ただしこれを使うと、区画外への射撃は現在の反撃例外に制限されます。軍共有は「情報を全軍から得る」であり、「任務による射撃制限まで無くす」こととは分けるべきです。`BattleWeaponOrders.cpp:20`、`BattleWeaponOrders.cpp:29`

**3. 観測と真の位置の境目**

- 2026-11-26 修正：本人の CanSee 相当の確認に成功した候補は本人の現在の目撃として扱い、その時点の目標の照準点（現在位置・姿勢・露出部位）を狙う。失敗時は更新せず、射撃待ちは最後の確認位置を保持する。軍共有表・通常接触とその期限は書き換えない。

今回の静的調査・記録追加（ビルド・UE・試合は未実施）：

- 修正前は本人確認成功後も共有の最終観測位置（非追跡は5秒未満）／追跡試料へ撃っていた。弾の散らばりは通常と同じ `Fire` → `ShotDirection` であり、known_fire専用の精度低下係数はない。姿勢・移動・制圧・照準安定の影響は共通。
- 通常位置は既存の交戦経路が優先、覗きも既存目標の本人確認が先。ただし追加射撃で弾薬・射撃間隔・照準状態を共有するため、その後の通常射撃を減らす可能性はある。0.4秒ごとの再選択に目標維持の加点はなく、向きの変化で照準安定が切れたり射撃時刻が延びたりする。目標維持・予算の変更は今回見送った。
- 候補の再生成は0.4秒間隔。予算保留は毎フレームの再要求も数え、命令拒否は探索中の候補ごと・選択再確認でも加算する。30万／120万は兵や弾の件数ではない。予算は陣営ごと0.1秒に32本、本人確認と銃口確認は別々に消費し、後者で保留すると再開時に本人確認からやり直す。
- `metrics.json` の `cover_diagnostics` に `known_fire_hits`／`known_fire_damage` と比較用 `ordinary_fire_hits`／`ordinary_fire_damage` を出す（切替1のみ）。命中は既存Hitsと同じ「兵の当たり判定に当たった数」で、装甲で損害0も含む。損害はHPの実減少量、小数保持・過剰損害除外・シールド吸収と本拠地は除外。ordinary は共通Fireを通るknown_fire以外（プレイヤー・制圧等も含む）。既存TeamDamageは別定義なので単純な差し引きには使わない。
- 既存の射撃距離は実際の射撃目標ではなく小隊目標の最終観測位置への距離。49mという中央値だけではknown_fireの距離別精度を判断できない。損害低下への各要因の寄与は今回の静的調査では確定できない。
- 一律+35cmの狙いは、しゃがみの当たり上端+20cm・伏せの上端−35cmより高く、`Fire` の頭上通過判定で外れる要因だった。成功したセンサーの終点を使い、姿勢別照準（しゃがみ−10cm・伏せ−60cm）と露出部位を通常射撃同様に扱う修正を含めた。
- 固定場面は27項目へ更新。追跡の有無にかかわらず現在位置へ照準、姿勢別照準、待ち時間中の保持、古い狙いだけが壁の裏、目は通るが銃口は遮られる場合、命中・実損害と通常射撃の計数分離を検査する。実行結果は未取得。

ご提案の「観測で候補を絞ってから、CanSee で実位置を確かめる」は妥当です。ただし、契約は次のように限定します。

> 候補の生成・順位・移動先は、軍が取得済みの観測情報から決める。候補の実位置を読むのは本人のセンサー判定と、SpotTrack が明示的に許可する知覚側の追跡更新だけ。センサーに失敗した敵の実位置・生死を、順位・移動先・記憶の更新へ戻さない。

`CanSee` は現在位置・生存・視距離・視野を確認してから光線を飛ばすため、この「センサーの中」の境界に置けます。`BattleLeaderRuntime.cpp:353`、`BattleLeaderRuntime.cpp:391`

注意点は二つあります。

- **CanSee の成功は、発見待ち時間を含む通常の知覚更新と同じではありません。** 今回は「軍から知らされた候補を本人が即時確認できる」という認識ルールの追加として扱います。
- CanSee の成功と、銃口から確認した現在位置への射線は別です。目から見えても銃口の前に壁がある場合を除くため、AimPosition への射線も確認します。

追跡については、既存実装が明示的に「射撃に使わない・報告へコピーしない」としています。今回の変更ではその例外を次の範囲に限ります。`BattlePerception.h:22`、`BattleTactics.h:57`

- `KnownTargetFire > 0` の候補位置・狙い・射撃位置探しだけ、期限内の `TrackedPosition` を使用。
- 追跡の生成は引き続き知覚側。射撃側が `Position(TargetID)` を取り直して追跡を更新しない。
- 元の観測時刻、追跡期限、接触の記憶期限を引き継ぐ。共有しても寿命を延ばさない。
- 追跡中でも本人の CanSee を省略しない。壁越し射撃の許可にはしない。
- 手りゅう弾・砲・制圧射撃・ミニマップなど既存の消費先は変更しない。

現状では追跡時間を長く指定しても、元の接触が記憶から消えれば終了します。また、追跡位置は知覚走査時の位置で、常時更新の真値ではありません。`BattlePerception.cpp:227`、`BattlePerception.cpp:231`

非追跡候補の期限は、まず **元情報の期限と5秒の短い方**を提案します。追跡候補は元の追跡・記憶期限に従います。期限切れの候補には CanSee を呼びません。

**4. 値2：小隊の任務内で、兵ごとに短く動く**

値2は値1を含み、**本人が撃てる候補を持たない場合**に、近場の射撃位置を探します。「小隊の誰かが撃てれば全員移動禁止」にはしません。ただし同時に動く人数を制限します。

初期案は次のとおりです。

| 移動距離 | 開始地点から10m以内。覗き点も含める |
| 小隊からの離隔 | 小隊中心から30m以内 |
| 同時移動 | 1小隊2人以下、かつ生存兵の半数以下 |
| 再探索 | 1秒間隔。終了後5秒は新しい位置取りを始めない |

`SoldierMove` は既に「兵単位・小隊の区画内・中心から30m以内・同時移動は半数まで」という構造です。ただし隠れている兵に限定され、援護できる遮蔽中の味方も必要なので、そのまま呼ぶと「誰も撃てない」場面を解決できません。`BattleSoldierMove.cpp:51`、`BattleSoldierMove.cpp:61`、`BattleSoldierMove.cpp:85`

射撃位置は「候補位置へ線が通る」だけでなく、**そこまで移動できる・占有されていない・射程内・任務範囲内**を必須とします。最初は直線の短い移動のみとし、壁の裏へ回り込む新しい個別経路探索までは入れません。

遮蔽スロットを優先し、無ければ少数の自由位置を調べます。自由位置は、現在地より観測上の危険が大きい場所を避けます。到着後は値1の本人確認をやり直し、敵がもう見えなければ撃ちません。

特に、`StartCoverApproach` は現在、本人の接触が古い／無いと中断し、到着時には再び `RequestCoverAction` を呼びます。新経路では **選んだ TargetID・観測情報・スロット・覗き点を引き継ぐ**必要があります。`BattleCoverAction.cpp:507`、`BattleCoverAction.cpp:520`、`BattleCoverAction.cpp:543`

移動の優先順位は、直接操作・個別移動命令・撤退・補給・突撃などを上位に置きます。KnownTargetFire 用の移動中は通常の経路移動を重ねて実行させません。現状の `Approaching` は条件によって通常移動を止めないため、ここも接続箇所です。`BattleLeaderRuntime.cpp:1235`、`BattleLeaderRuntime.cpp:1244`

情報が期限切れになった場合は追跡を打ち切り、選択済みの近い安全な遮蔽まで退避してから任務へ戻す設計を推奨します。命令が変わった場合は直ちに新命令を優先します。

**5. 光線と探索の予算**

ゲーム上の規則と処理予算は、設定・記録を分けます。予算不足を「撃てない敵」と判定しないことが重要です。

初期案：

| 処理 | 上限案 |
|---|---|
| 軍共有表 | 知覚更新結果から陣営ごとに集約。兵ごとの全件走査は禁止 |
| 候補選択 | 兵ごとに0.4秒間隔、上位3件 |
| 本人確認 | 1回の選択で最大3候補。最初の成功で終了 |
| 発砲前確認 | 発砲可能時に選択目標1件を確認。同じ位置・姿勢・時点の結果は共有 |
| 値2の探索 | 兵ごとに1秒間隔、目標最大2件・位置最大6件 |
| 全体予算 | 新機能分の実光線を1陣営あたり0.1秒で32本から開始。移動探索はうち16本まで |

候補・兵の処理順は安定した順序と巡回方式にし、低い UnitID だけが毎回予算を取らないようにします。上限に達した場合は `Deferred` を返し、次の機会へ持ち越します。

**候補数を絞るだけでは光線予算になりません。** `ExposureAt` は5点を調べ、`HasTerrainLine` は兵の当たり判定を飛ばすため追加の光線を最大8回行います。`CoverFirePoint` 内にも複数の候補・Sweep があります。実際のトレース呼び出し単位で予算を消費し、Sweep・Nav投影は別カウンタで制限する必要があります。`BattleTactics.cpp:348`、`BattleTactics.cpp:362`、`BattleCoverAction.cpp:132`

この予算は追加機能分の上限です。既存射撃・知覚を含む総負荷の上限ではありません。

**6. 記録**

既存の `cover_diagnostics` に `known_fire_*` と `known_move_*` を追加できます。記録は `SightExperiment.Enabled` のときだけ有効なので、試験スクリプトで確実に有効化します。`BattleSightExperiment.h:65`、`BattleSightExperiment.cpp:220`

最低限、次を分けて数えます。

- `candidates`：鮮度・命令・距離で絞った候補件数
- `sensor_checks`／`sensor_rays`：確認回数と実光線数
- `reject_stale`／`reject_order`／`reject_range`／`reject_fov`
- `reject_sensor_wall`／`reject_aim_wall`：実位置の視線と狙い位置への射線
- `budget_deferred`：予算による保留
- `shots_open`／`shots_peek`：`Fire` が成功した弾数
- `tracked_candidates`／`tracked_shots`／`tracked_move_plans`
- `move_started`／`move_arrived`／`move_arrived_fired`
- `move_cancel_*`：命令変更・情報期限・詰まり・予約喪失など
- `move_distance_cm`、移動時間、到着から初弾までの時間

`move_arrived_fired` は「到着した移動エピソードで、選んだ目標へ初めて実弾が出た」を1回だけ数えます。別目標を撃った数は分離します。

なお、現在の CanSee は bool なので、失敗をすべて「壁」に数えてはいけません。既存の `PrepareSightTrace`／`TraceSight` を使う結果付き判定を追加し、視野・距離・無効目標・遮蔽を区別します。`BattleLeaderRuntime.cpp:391`

**7. 固定場面**

新設案は `Setup/Test-KnownTargetFire.ps1` と `BattleKnownTargetFireTrial.cpp`。既存の壁生成・検査ログ・結果JSON・機体情報・タイムアウトの構成を参考にします。既存試験は兵なしの幾何試験なので、今回は実兵の射撃まで通す試験を追加します。`BattleCoverFirePointTrial.cpp:11`、`Setup/Test-CoverFirePoint.ps1:11`、`Setup/Test-CoverFirePoint.ps1:20`

| 場面 | 必須の確認 |
|---|---|
| 別小隊だけが発見 | 射手に本人の目撃が無くても、軍共有→本人確認→実射撃。通常位置と覗き位置の両方 |
| 第一候補は壁の裏 | 第一候補を拒否し、第二候補へ実射撃。第一候補の失敗で終了しない |
| 古い報告 | 期限切れ候補へ確認も発砲もしない。表の再構築・再配信で鮮度が復活しない |
| 全員がその場では撃てない | 値1では移動ゼロ。値2では近い有効位置へ移動し、到着後の本人確認を経て発砲 |
| 追跡あり／なし | 遮蔽後に敵を移動。候補・狙いがそれぞれ追跡位置／最終観測位置になる。追跡中でも壁越しには撃たない |
| 移動競合・任務 | 同じスロットの二重取得なし。人数・距離制限、Hold、個別命令、撤退、命令変更を確認 |
| 予算枯渇 | 上限を超えず保留になる。後ろの兵にも順番が回る |
| 匿名・未配信の偵察情報 | 真値からIDを補完しない。報告前には射撃候補にならない |

乱数による命中だけを合否にせず、選択ID・実発砲・使用した狙い位置・移動終了理由を検証します。新機能の試験結果は `BATTLE_KNOWN_FIRE_RESULT failures=0`、基本回帰は既存の `BATTLE_SMOKE_RESULT failures=0` で別に確認する構成です。

**9. ユーザー判断が必要な点**

設計を止める必要はありませんが、実装時の初期設定として次を決めると曖昧さがなくなります。

| 判断点 | 推奨 |
|---|---|
| 移動距離 | まず10m。15m以上は固定場面と発動結果を見てから |
| 守りの兵 | Defend は防衛範囲内で許可。明示的な Hold は移動させず値1だけ |
| 攻撃移動中 | 初期段階は交戦停止中・持ち場到着後に限定。進軍途中からの離脱は後で評価 |
| 群の任務 | 担当区画・持ち場内だけ。集合中・撤退中・突撃中は位置調整しない |
| 区画外の既知敵 | まず既存の命令制約を守る。軍共有を理由に制約を解除しない |
| 非追跡情報の鮮度 | まず最大5秒、元情報の期限を超えない |
| 対象武器 | 最初は通常の小銃・支援銃。対戦車・間接火器は既存専用AIを維持 |
| 遮蔽が無い場所への移動 | 観測上の危険を増やさない近場だけ許可 |
| CoverFirePoint との関係 | 新経路では over/lean 判定を再利用し、他の兵の遮蔽ルールを一括変更しない |

特に値2では、「撃てる位置がある」と「そこへ行く価値がある」を分ける必要があります。既存の CoverFirePoint 試験でも、射撃が増える一方で遮蔽外の被弾が増えています。射撃数だけで採用を判断せず、移動後の初弾成功率と移動中・到着後の損害を併せて見る設計が適切です。`Docs/experiments.md:28`
