# 計測ロックの順番待ちを自動にする（作業の進め方の設計案）

2026-11-22 1時45分 Claude（ロードマップに従う改善活動）。**設計案のみ。採用はユーザー判断**（全セッションの進め方が変わるため）。

## 1. 困っていること

- ビルド・UE の起動・計測は、CPU を共有するので1つずつしかできない（`MEASURE.md` 0-1）。今はロックをチャット（`SendMessage`）で受け渡している。
- 11-22 の夜は、ロックの順番待ちが 個人AI → Codex委任 → 区画AI → この作業 と並び、この作業は 23時55分に並んで 2時30分ごろの番になった。待つ間、ビルドも試合もできない。
- 受け渡しのたびに、渡す側・受ける側の Claude がメッセージを書く・読む手間（使用量）がかかる。持ち主が寝てしまう（ターンが終わる）と、次の番に渡らないことがある。
- 誰が持っているか・あと何分かが、チャットの履歴をたどらないと分からない。

## 2. 案：ファイルで持つロックと順番待ちの列

`Setup/Lock-Queue.ps1`（PowerShell。どのセッションからも同じものを呼ぶ）。

| 呼び方 | 働き |
|---|---|
| `Lock-Queue.ps1 -Join -Who <セッション名> -Purpose <用途> -Minutes <見込み>` | 列の最後に並ぶ。列と持ち主は `C:\Users\nanek\Documents\FPS\.lock\queue.json`（作業ツリーの外。どの作業ツリーからも同じ場所） |
| `Lock-Queue.ps1 -Wait -Who <名>` | 自分の番になるまで待つ（30秒ごとに見る）。番が来たら持ち主に自分を書いて終わる。Claude は `run_in_background` で呼び、終わりの通知で番が来たと分かる |
| `Lock-Queue.ps1 -Release -Who <名>` | 手放す。次の人が持ち主になる |
| `Lock-Queue.ps1 -Status` | 持ち主・始めた時刻・見込みの終わり・列を表示 |

- **期限**：持ち主が見込みの時間＋30分を過ぎても手放さず、その間に UE・ビルドのプロセスが動いていなければ、次の人に渡す（寝てしまった持ち主で列が止まらないように）。動いていれば延長して、持ち主へメッセージを送る案内を出す。
- **割り込み**：ユーザーの画面での確認（プレイ）は最優先。`-Join -Urgent` は列の先頭に入る（持ち主の作業は止めない）。
- **記録**：受け渡しの履歴を `queue-log.jsonl` に残す（何分待ったか・何分使ったかが後で分かる）。
- 既存の決まり（他のセッションのプロセスを止めない、実行を重ねない）はそのまま。ファイルのロックは「目印」で、強制はしない。

## 3. 移行

1. スクリプトを main に入れ、`MEASURE.md` 0-1 の手順を「`Lock-Queue.ps1 -Join` → `-Wait`（裏で）→ 作業 → `-Release`」に書き換える。
2. 各セッションへ一度だけ周知する（以後はメッセージでの受け渡しは不要。急ぎの相談だけメッセージ）。
3. `/measure` スキルの段取りにも入れる。

## 4. 合わせて考えたいこと

- 描画なしの試合は並列で回せるので、短い確認（1〜2試合）を「相乗り」できるようにする案：持ち主が許せば、列の次の人の描画なしの試合を同時に流す（`-Share` で「相乗り可」を示す）。CPU の空きを使えるが、時間の比較には使えない試合になるので、勝ち負けの比較や一致の確認だけに限る。

## 5. 作業の列と試合の枠（2026-11-25、ユーザー決定。`Docs/design-match-budget.md` 8.1）

11-22〜11-25 の集計で、待ちを決めているのは試合の本数ではなく「回」（ビルド＋回帰試験＋試合1バッチ）の数で、試合が流れている時間の半分は並列4本以下だった。凍結ビルドの写しから起動する描画なしの試合は、ほかのビルド・ほかの試合の影響を受けない（下の確認）ので、列を2つに分けた。

| 種類 | 何を入れるか | 呼び方 |
|---|---|---|
| **作業の列**（1つずつ。今までの列） | ビルド、回帰試験（`Test-Battle` と専用試験）、main への取り込み、マップの生成、凍結ビルドを作る | `-Join -Who … -Purpose … -Minutes …` → `-Wait` → 作業 → `-Release`（今までと同じ） |
| **試合の枠**（全体で12本まで。系統をまたいで同時、作業の列の持ち主とも並ぶ） | 凍結ビルドから起動する描画なし・30FPS の試合だけ | `-Join -Who … -Matches <本数> -Purpose … -Minutes …`（空きがあればその場で `ACQUIRED_MATCHES`、無ければ `-Wait`）→ 試合 → `-ReleaseMatches -Who …` |
| **単独** | 性能・描画ありの計測（時間を比べるもの） | `-Join -Alone …` → `-Wait`（流れている試合が終わってから戻る。待っている間・持っている間は新しい試合が始まらない）→ 計測 → `-Release` |

- 1回の典型：作業の列で「ビルド＋回帰試験＋`New-BattleBuildSnapshot`」→ **`-Release -Who … -ToMatches <本数> -Minutes <見込み>`**（作業の列を手放し、そのまま試合の枠へ。枠が埋まっていれば先頭で待つ）→ 試合 → `-ReleaseMatches`。試合の間に次の系統がビルドを始められる。
- ビルドの要らない試合（既にある凍結ビルドで条件だけ変える）は、作業の列に並ばず `-Join -Matches` だけでよい。
- 試合の枠で流してよいのは、**凍結ビルドから・描画なし・時間を比べない**試合だけ。作業ツリーから直接起動する試合（動作を見る1本など）は、今までどおり作業の列の中で流す。
- 同じ名前（`-Who`）で、試合の枠に入ったまま作業の列にも並べる（試合の間に次のビルドの順番を取る）。
- 見込み＋30分を過ぎ、UE のプロセスが1つも無い試合の枠は外れる（寝てしまったセッションで枠が埋まらないように）。
- 置き場所：試合の枠は `FPS\.lock\matches.json`。`queue.json` の形は変えていない（変更の前から待っている古い `-Wait` が古い形で書き戻すため。`-Alone` は既存の `share` の欄に `alone` と入れている）。履歴は同じ `queue-log.jsonl` に `mjoin`・`macquire`・`mrelease`・`mstale`・`mleave` として残る。

- **前提の確認（11-25 11時38分〜12時11分、凍結ビルド `joinfight1-111753`、30FPS・描画なし）**
  - 単独の4試合（マップI・K × シード7・43、`idchk-alone-*`）と、同じ4試合を「埋め草8試合（計12本）＋ `FutureBattle-budget` の初回の全ビルド＋ `Test-Battle`」と重ねたもの（`idchk-load-*`）を `Compare-MatchResults.py` で比べ、**4組とも `IDENTICAL`**（時間を除く78項目）。実時間は1試合 310〜347秒 → 506〜548秒（約1.6倍）。埋め草8本も合格。全ビルドは741秒で成功。
  - `Test-Battle`：単独は84秒で `failures=0`。**12試合と同時（ビルドなし）は112秒で `failures=0`**。**12試合＋全ビルドと同時は180秒の時間切れ**（試験の失敗ではなく、起動が間に合わなかった）。作業の列は1つずつなので、ほかの系統のビルドと自分の回帰試験は重ならない。
  - 確かめていないこと：`Test-Battle` 以外の試験（`Test-Area` など）が12試合と同時に時間内に終わるか。描画ありの試験。
