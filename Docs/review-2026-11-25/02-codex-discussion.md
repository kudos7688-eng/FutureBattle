### A．契約の修理を先にする：賛成。ただしB10を分離

順番は **B03 → B06 → B01/B02 → B04** でよいと思います。B10は別の変更として扱います。

**懸念1：切替なしで直せる範囲**

「結果が変わるか」だけではなく、**正しい動作を勝敗とは独立に決められるか**で線を引くのがよいです。

| 分類 | 扱い | 今回の例 |
|---|---|---|
| 明示された契約への違反 | 新しい切替なしで修正 | 予備資源を割らない、補給後も区画任務を保つ、正当な状態を保存できる |
| 保存する値の欠落 | 新しい切替なしで修正。ただし旧保存の扱いを決める | 主砲の発射番号、残り待機時間 |
| 複数の正当な動作から一つを選ぶ変更 | 独立した挙動変更として判断 | 全兵の更新順をUnitID順に変える |
| 戦術・知覚ルールの変更 | 既存の試験切替で評価 | Observed系、SectorSight |

これは**今後の例外規則として合意する案**です。既存の「挙動変更は既定0」を、実装担当が独断で読み替えるべきではありません。

B03は購入後の資源という局所的な条件で正否を判定できます。委任経路だけ購入費を含めていないことが根拠です（`BattleArea.cpp:449–451`）。勝敗が悪化しても、予備資源を守らない実装へ戻す理由にはなりません。

ただし、**B03で通常の無委任AI戦まで変わるとは限りません**。直接の変更対象は委任購入です。修正対象外の条件でも結果が変われば、変更範囲を疑うべきです。

**B10は一律UnitID順を即採用しない。** 保存後に走査順が変わる問題はありますが、UnitID順は唯一の正解ではなく、先に処理される陣営・個体への有利不利も起こし得ます。現在も命令・雇用順による陣営差の履歴があります（`STATUS.md:18`）。

まず「保存前後で実効的な処理順を維持する」を契約にし、順序の保存と正規順序への統一を比較してください。後者を選ぶなら別コミットで、両陣営への影響を確認します。毎フレーム全件ソートする実装も避けたいです。

**懸念2：B01の重大度は中に修正します。**

直接操作専用で、AI兵は使わないことがコードに明記されています（`BattleWallCover.cpp:12–15`）。したがって「通常のAI試合の保存を広く壊す高重大度」という扱いは過大でした。

一方で、プレイヤーが普通に壁へ隠れただけで保存不能になるため、次の試遊前には直したい問題です。生成される80cmの覗き位置と保存検査の100cm下限が食い違っています（同`:26–27`、`BattleSave.cpp:161`）。**重大度は中、試遊前の優先度は高め**とします。

**懸念3：B07は後回しでよい。削除の根拠には不足。**

既定0のBoundingを次の試遊で使わないなら、今週の必須項目から外してよいです。ただし、遮蔽処理の早期returnで交互前進の処理に届かない不具合があるため、その状態で得た「効果なし」は機能廃止の根拠にできません（`BattleLeaderRuntime.cpp:890–893, 960–962`）。

「修理して評価する予定がないので休止」は妥当です。「弱いから削除」は現時点では支持しません。

### B．最初は元任務の構造体と復帰関数：賛成

これより小さく、有効な最初の一歩は思い当たりません。ただし、単なる重複除去で終えず、次の契約を入れたいです。

- 補給開始時に一度だけ元任務を保持する。
- 補給中に新しい明示命令を受けたら、古い任務へ戻さない。
- 復帰は一度だけ行い、命令・目的地・区画属性をまとめて戻す。

現在は復帰時の `IssueOrder` が区画属性を渡さず、既定のfalseで上書きします（`BattleSquadRetreat.cpp:164,188`、`BattleLeaderRuntime.h:616`、`BattleState.cpp:214`）。

構造体に将来必要そうな項目を大量に入れる必要はありません。ただし、**古い任務への復帰を防ぐ命令世代番号等の照合**は検討対象です。新規命令による解除が既に保証されているなら、その仕組みを使います。

全命令の裁定一本化は、その後でよいです。

### C．発動確認：修正して賛成

**「狙った行動が1回以上なければ採否に使わない」には反対です。**

発動ゼロには、対象がいなかった場合と、対象がいたのに仕組みが働かなかった場合があります。後者を除外すると、成功しやすい試合だけが残ります。

次の二つを分けてください。

- **機能の動作確認**：対象条件を用意し、発動することを短い専用試験で確かめる。
- **通常試合での有用性**：発動ゼロも含め、事前に決めた試合をすべて集計する。

購入も同様です。既存部隊や初期配置に対する変更なら「購入された」は必要条件ではありません。対象部隊が存在し、必要な状況に遭遇したかを見るべきです。

追加費用を抑える手順は以下です。

1. **既存ログで対象の存在と発動を確認する。** 同じ凍結ビルド・条件の合格済み結果は再利用する（`MEASURE.md:43`）。
2. 発動が確認できなければ、長い試合を増やさず、短い専用条件で確認する。
3. 通常試合はまず既存の2シードで基準との差を見る。対象・発動回数も併記する。
4. 採用候補だけ、事前に固定した未使用2シードで確認する。全マップ・左右の総当たりは義務化しない。
5. 未測定のマップ・側を表に明記する。向きが割れた場合だけ、判断に必要な条件を追加する。

既存ログで使えるものは次です。

| 確認内容 | ログと注意点 |
|---|---|
| 購入実績 | `BATTLE_AREA_HIRE` の `team/type/squad`（`BattleArea.cpp:155`） |
| Planner購入成功 | `BATTLE_COMPOSITION_EXECUTE success=1`（`BattleCompositionRuntime.cpp:191`）。購入ログと二重計上しない |
| 委任予約の実購入 | `BATTLE_HIRE_RESERVE op=buy by=AI`（`BattleArea.cpp:336`）。`op=add`は発動成功ではない |
| 詰め寄り・突撃開始 | `BATTLE_ARMS_ASSAULT`、`BATTLE_ARMS_CHARGE`（`BattleArms.cpp:481,538`） |
| 投擲・近接実行 | `BATTLE_ARMS_GRENADE`、`BATTLE_ARMS_MELEE`（同`:690,815`） |
| 第二重点への群配分 | `BATTLE_FRONT_FOCUS2_GROUP`（`BattleGroups.cpp:361`）。重点選択だけとは区別する |
| 前線の進退 | `BATTLE_FRONT_ORDER_STEP`（`BattleFrontLine.cpp:409`）。到着成功そのものではない |

勝敗・損害の差分は既存の `Analyze-MatchDelta.py` を使えます（`MEASURE.md:30`）。ログ行数は保存復元によるカウンタ再開や重複にも注意し、可能なら部隊ID・イベント単位で数えます。

### D．観測原則：賛成。既定化は条件付き

境界は次のように書くと曖昧さが減ります。

> 敵に関する判断は、取得元・取得時刻・共有範囲が明確な観測情報を使う。自軍状態と公開ルール情報は利用できる。衝突・命中・損害解決は真値を使えるが、その結果を未観測の敵情報として判断へ逆流させない。

「物理処理だから真値可」だけだと、経路評価や目標選択まで物理扱いにして抜け道ができます。

**ObservedArmour／ObservedTacticsを今週まとめて既定1にすることには反対**です。既存切替を使って一つずつ確認します。特にObservedTacticsは、保存後に接触の出所を保守的に変更し、保存往復の完全一致を保証しないと明記しています（[design-observation.md:14](C:/Users/nanek/Documents/FPS/FutureBattle/Docs/design-observation.md:14)）。Aの保存継続性と先に整合させる必要があります。

また、公平な情報制約を採用するかはゲームルールの判断です。**不正確な真値利用よりスコアが下がった、という理由だけで不採用にすべきではありません。** 動作停止・極端な反応遅延・負荷悪化は別途確認します。

SectorSightの発見漏れ指標には賛成ですが、既存の `BATTLE_SECTOR_SIGHT skipped` は省いた候補数であり、見えていたはずの敵数ではありません（`BattleScoutReport.cpp:71`）。最初は短い固定場面で「敵出現→初回接触までの時間」「隊長不在時に発見できるか」を確認する方が安いです。全兵に追加LOSを走らせる計測は後回しにします。

### E．整理：賛成。証拠は消さない

削除候補をユーザー判断に出す方針でよいです。ただし、まとめて削除する一件にはしない方が安全です。

- `FollowSightParallel`：本体の受け口がない引数の整理。
- `LeaderAbilityScale`：参照が薄くても、保存・反映プロパティとの互換性を確認してから削除。
- 旧Strategy群：後継への置換と、旧結果の再現に必要なコミットを明示して判断。
- VATFarLight／SectorNoRoad：評価結果と残す利用者の有無を添えて判断。

STATUS要約の修正は先に行う価値があります。実装済み・未実装・既定値の混在が次の担当者の誤判断につながっています。

### F．引き算評価と到着見積り：賛成

「購入・運用込みの損得」という読み替えが正確です。兵種を除くと代替購入、資源待ち、配備時刻まで変わります（`BattleArea.cpp:420–428`）。兵種固有の強さだけを取り出した値ではありません。

Plannerの見積り変更を実測後にすることにも賛成です。ただし、**一度の計測で一部隊だけ見るのは不足**です。一つの短い計測内で、直線的な道と迂回路を数件採れば十分です。

さらに「移動開始→到着」と「購入→到着」を分けます。現在の見積りは距離の補正と固定時間を使っています（`BattleCompositionRuntime.cpp:169–173`）。誤差の主因が命令待ちや詰まりなら、区画グラフ距離への変更では直りません。

### G．操作の通し確認：賛成。自動指標は定義してから

次の試遊で確認する流れは適切です。保存修理をするので、**壁遮蔽中の保存・復元**も追加したいです。

一方、動き出し時間と上書き回数は、そのまま数えると誤解を招きます。

- 動き出し時間：移動が必要な命令を受理してから、目的に沿った移動を開始するまで。既に到着済み・保持命令・正当な待機は分ける。
- 上書き回数：同じ命令の再発行は除外し、発行元・理由・命令世代を記録する。補給や被弾による正当な中断と、意図しない競合を区別する。

### 追加質問への回答

**1．前回提案で修正したいもの／費用対効果が低いもの**

前回の「BodiesをUnitID順に固定」は踏み込みすぎでした。必要なのは保存前後の順序の一貫性であり、UnitID順への全面変更は別の設計判断です。B01の重大度も中へ修正します。

A〜Gのうち今週の費用対効果が最も低いのは、**DをObserved系の一括既定化と全体的な発見漏れ計測まで進めること**です。原則の明文化と少数の専用確認には価値がありますが、大規模な計測・既定化は保存修理後に回します。

**2．落ちている重要事項**

- **保存継続性の合格条件**：同時刻の即時往復だけでなく、過去の保存への巻き戻し・新規プロセスでの読込を区別する。主砲番号の問題は即時往復だけでは見逃し得ます（`BattleTankGun.cpp:142`）。
- **旧保存との互換性**：不足項目の既定値、形式の版、対応する範囲を決める。B04だけで全シミュレーションの完全再現を達成したとは扱わない。
- **評価条件の固定**：ビルド、実効切替、マップ、FPS、保存往復条件を揃える。既存のRulesKeyだけで全挙動設定を識別できるとは限りません。
- **B05の移動停止**：通し試遊で再現するなら、観測ルールの追加評価より優先する。ただし試験修正をそのまま既定化しない。
- **B09**：SectorSight=2を評価する前に修理する。既定1の検討だけなら今週は後回しでよいです。
