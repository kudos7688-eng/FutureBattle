## 1．8点への評価

### ① 遊べる一本より先に系統を広げている：賛成。ただし「磨く」より「つなぐ」

根拠は十分あります。

- 兵種10種類が揃っている一方、群操作・補給・区間命令・表示などで実画面確認が残っています（`ROADMAP.md:9–18`、`STATUS.md:13–25`）。
- `SWITCHES.md:7`は**起動引数497種類**。今回数えた `-Battle…` の行だけでも449あります。すべてが独立した実験切替ではありませんが、組み合わせを人が把握するには大きい数です。
- 前線統合は段階4が混在、5は未発動、6は不採用、7は画面確認待ちのまま次へ進んでいます（`Docs/design-front-strategy.md:11–18`）。

ただし、H/I/Jのような異なる地形は、汎用的な移動・戦術を確かめるための試験資産です。単に「マップ数を減らす」とはしません。

今必要なのは最終品質の垂直スライスより、**一つの代表マップで、指揮→交戦→補給→個人操作→指揮復帰が成立する試遊版**です。見た目の完成を待たず、手順と既定条件を固定する方が先です。

なお、引用された実務記事自体も垂直スライスには単一の定義がないとしています。「業界共通の厳密な工程」とするより、検証目的を分ける参考として使うのが適切です。[実務記事](https://www.gamedeveloper.com/game-platforms/what-you-should-take-out-of-pre-production)

### ② AI同士の勝敗を主な物差しにしている：歴史的には当たる。現方針は改善済み

現在の `MEASURE.md:26–29` は、勝敗だけでなく、基準との差・損害・撃破・戦死・得点内訳を要求しています。**「今も勝敗だけで採否を決めている」は不正確**です。

一方、欠けているのは以下です。

- 指示を理解して出せたか。
- FPS操作中に、指揮へ戻る必要がどれだけ生じたか。
- 命令した部隊が動かない理由を理解できたか。
- 戦闘の間・射撃頻度・危険の分かりやすさが適切か。

直近の小銃射撃の記録でも、損害増加だけでなく、実際の射撃頻度が問題になっています（`STATUS.md:36–53`）。これは勝敗では測れない体験です。

**契約の正しさ／通常戦での効果／プレイヤー体験を別の合格条件にする**のがよいです。2022年の調査論文も自動試験の課題を論じていますが、それだけで「現在の自動バランス検査全般が未成熟」と断定するのは広すぎます。[研究論文](https://arxiv.org/abs/2202.12777)

### ③ 描画フレームとシミュレーションが結びついている：強く賛成

正確には、**通常のWorld Tickに戦闘処理が結びつき、独立したシミュレーション時計がない**構造です。

| 箇所 | 確認できた依存 | 影響 |
|---|---|---|
| `BattleGameMode.cpp:169–172` | TickのDeltaTimeをそのままRuntimeへ渡す | 戦闘更新の機会がWorld Tick数に依存 |
| `BattleLeaderRuntime.cpp:1612,1662` | NowはWorld時刻、Followだけ `Min(Dt,.05)` | 50msを超えた分だけ移動側の時間を捨てる |
| 同`:1627–1628,1664–1666` | シールド・砲弾・Armsは元のDtを使用 | 遅いフレームで処理系ごとの進む時間が異なる |
| `BattleStableMovement.cpp:643–649` | 個人経路探索は最大2件／`GFrameCounter` | 上限は30FPSで毎秒60件、60FPSで120件。実際に使う数とは別 |
| `BattleLeaderRuntime.cpp:1045–1055` | 遮蔽探索もフレームごとの予算 | 混雑時の待ち時間がFPSで変わる |
| 同`:1634–1642` | `BattleThinkCap` はStep単位 | 既定0だが、有効時は処理能力がFPS依存 |
| `BattlePerception.cpp:304–335` | 時刻で走査期限を管理するが、実行はWorldフレームごと | 期限の丸め・遅延・停止後の取りこぼしが生じる |
| `BattleLeaderRuntime.cpp:1768–1773` | 被弾方向の誤差に `GFrameCounter` を使用 | 該当機能有効時は同じ被弾でもフレーム数で推測位置が変わる |

重要な訂正は、**30FPSと60FPSの差をDt切り詰めだけでは説明できない**ことです。両者とも通常のDtは50ms未満です。探索予算、走査時刻、衝突の刻み、処理順なども関係します。

また知覚は「毎フレーム全員のLOSを測る」実装ではありません。0.2／0.4秒の期限を持ち、個体ごとに分散しています。ただし期限を迎えた位置を読む時点はフレーム依存です。

**最小の一歩と費用**

1〜2日なら、変更ではなく次を一覧にするところまでです。

- World時刻・Dt・フレーム番号を使う戦闘処理。
- フレーム単位の予算と、秒単位に換算した上限。
- 時刻を保存する状態と、遅延時に捨てる処理。
- 表示・入力・CharacterMovementと切り離せない箇所。

その後の最小実装は、**明示的な戦闘時計とTick番号を一系統へ渡せる入口を作ること**です。いきなりStep全体を固定刻みループへ入れても、内部がWorld時刻や同じActor位置を読むままなら正しくなりません。

全体移行は1〜2日の仕事ではありません。入力、Actor移動、衝突、砲弾、保存、追いつき処理、表示補間まで関わります。固定刻みだけでUEの物理・ナビを含む決定性が得られるわけでもありません。

Supreme Commanderの「シミュレーション10Hz・表示別系統」は開発者の記事で確認できます。ただし、その10HzをFPS直接操作にそのまま当てはめる根拠にはなりません。[開発者記事](https://www.gamedeveloper.com/business/opinion-synchronous-rts-engines-2-sync-harder)

### ④ 切替に期限と持ち主がない：概ね賛成

STATUSには系統名があり、完全に持ち主不在ではありません。しかし `SWITCHES.md:9` の列は引数・読み方・推定既定・場所・コメントで、**採否の条件、見直す日、依存する切替、終了状態がありません**。

しかも一覧自身が、マップ・陣営・実行時の実効値を保証しないと明記しています（同`:4–5`）。ここに実験の寿命管理まで期待するのは無理があります。

新しい実験には「担当・目的・依存条件・見直し日・終了条件」を付けることに賛成です。ただし497項目全部に期限を付ける作業は不要です。診断・恒久設定・実験を分け、**新規と現在進行中のものから**始めます。短期と恒久の区別、作成時の撤去計画は外部の運用指針とも合います。[LaunchDarklyの指針](https://launchdarkly.com/docs/guides/flags/technical-debt)

### ⑤ 命令裁定が一つでない：部分的に賛成。B06とB07の根を同一視しない

- **B06**は任務属性の欠落と復帰処理の重複でした。現在は修理・専用試験が入りました（`BattleSquadRetreatSmoke.cpp:141–178`）。
- **B07**は、遮蔽行動の早期returnより後に交互前進の処理がある、個人行動の優先順位の問題です。
- **Purpose問題**は、目的拠点を保ったまま兵種固有配置を選ぶ入口がない問題です。設計文書も単純な `!Purpose` の解除では直せないと説明しています（`Docs/design-composition-ai.md:15`）。

したがって、巨大な「全命令裁定器」を先に作るより、**小隊の任務／一時行動／個人の実行状態の境界を明確にする**方が小さく進められます。入口が複数あること自体より、上書き権限と解除条件が曖昧なことが問題です。

### ⑥ 観測原則が商用標準より厳しく高コスト：その結論には反対

「商用の標準より厳しい」は、挙げられた資料では立証できません。Soren Johnsonの記事は知覚される公平さと透明性の話であり、**見えない場所では真値を使う設計を一般的に推奨しているわけではありません**。[原文](https://www.designer-notes.com/game-developer-column-7-our-cheain-hearts/)

FutureBattleでは、どの部隊にも降りられ、偵察と遮蔽に意味を持たせたいので、「ユーザーが気づかない場所」の境界も安定しません。

実際の費用は三種類あります。

| 費用 | このリポジトリでの実態 |
|---|---|
| 計算 | 本拠地の追加LOS、個人の観測接触からの回避候補構築など。ObservedTacticsの追加負荷は未計測（`Docs/design-observation.md:16`） |
| 状態管理 | 接触の出所・時刻・共有資格・配送待ちを保存・復元する必要 |
| 保守 | 自分で見た情報、分隊共有、偵察報告、真値を複数の読み手で使い分ける必要 |

ただし、**件数の多さとCPU負荷の大きさは別**です。分隊共有への変更では、マップIの配送件数152万→9.9万、報告処理0.096→0.006ms、AI全体1.60→1.51msと記録されています（[design-squad-knowledge.md:160](C:/Users/nanek/Documents/FPS/FutureBattle/Docs/design-squad-knowledge.md:160)）。大幅な件数削減ですが、主な価値を「大量のCPU時間を回収」とは言えません。

主砲の兵種判定を観測済みの型にするだけなら、既存の接触に属性を持たせて参照する変更です（`BattleTankGun.cpp:61–81`）。常に重い再探索が必要なわけではありません。

勧める簡略化は、**情報の正当性を保ち、通信の粒度・記憶の表現・再計算頻度を簡単にすること**です。隠れた敵の真値への依存を増やすことではありません。

### ⑦ 相性表を先に作るのが標準：提案には賛成、標準という断定は撤回

既に費用・役割・必要数・観測車両数に応じた購入設計があります（`Docs/design-composition-ai.md:48–94`）。「設計せず試合から数字だけ探している」は言い過ぎです。

不足しているのは、仕様と試験を結ぶ一枚です。

> 兵種／主な仕事／得意な相手／苦手な状況／必要な支援／費用／確かめる固定場面

これなら有効です。ただし射程、遮蔽、接近時間、補給、購入時期が効くゲームなので、**DPS÷価格だけの表から価格を決めない**こと。相性表は検証する仮説であり、完成したバランス表ではありません。

### ⑧ 長い試合ばかりで小場面がない：否定。使い分けには改善余地

現物を数えると、Prototypeに名前が`Smoke`を含むファイルが**25個**、Setupに`Test-*.ps1`が**40本**あります。すべて短時間とは限りませんが、専用試験が乏しい構成ではありません。

B06の復帰試験も、試合開始3秒後に起動し、その場で任務属性・一度だけの復帰・新任務への更新を確かめます（`BattleLeaderRuntime.cpp:1667–1669`、`BattleSquadRetreatSmoke.cpp:160–178`）。

改善点は、**既存の小試験を使って機能成立を確認してから、長い試合へ進む順序の徹底**です。移動停止や遮蔽配置は小場面、購入・補給・前線維持は長い試合が必要です。

2シードは大きな問題の選別には使えますが、広い一般化には弱い。その限界を明記すればよく、全変更で本数を増やす必要はありません。

## 2．Claudeが見落としている非効率

**最優先は、文書の現状と履歴の混在です。** STATUSは今回536,085 bytes、約524KiBでした。80KB目安の分割規則を大きく超えています。現在の要約にも「取り込み済み」と古い「未取り込み」が同居する行があります（`STATUS.md:13,18,24`）。読む量だけでなく、間違った前提で調査をやり直す費用が出ます。

次に、以下があります。

- **変更の比較条件が動きすぎる。** 「mainが17ファイル進んだため旧ビルドとの一致を比較できない」という記録があります（`Docs/design-squad-knowledge.md:161`）。各系統の局所試験に加え、合流後の代表条件を一つ固定する価値があります。
- **診断の成功とシミュレーション一致を混同しやすい。** `IDENTICAL`は非時間metricsの一致で、保存内容・状態全体の一致ではありません（`MEASURE.md:21`）。この定義は正しいので、報告側も省略しない方がよいです。
- **共有Runtimeへの集中と詰めた記法。** 現在の`.cpp/.h/.inl`は230ファイル・48,875行。最大はRuntime 1,993行、Controller 1,757行、HUD 1,726行です。240文字超の行は342行ありました。行数だけで悪いとはしませんが、時刻・保存・行動が同じRuntimeへ集中する方が並行開発の障害です。全体整形より、変更箇所の条件分岐を読みやすくし、独立した計算を抽出する方が先です。
- **新機能の保存方針が後追い。** 最新の指切り状態も保存せず読込時に空にすると明記されています（`STATUS.md:40`）。試験中としては選べる方針ですが、保存継続性が必要な機能には、実装開始時に「保存する状態／再構築する状態」を決めたいです。
- **CI不在は未確認。** 追跡ファイルから一般的なGitHub Actions・GitLab・Jenkins設定は見つかりませんでしたが、外部CIまでないとは断定しません。自動試験の入口は十分あるので、最初はローカルで変更分に応じた試験一覧を出す方が安いです。
- **単一マシンのロックは現状では合理的。** 描画性能測定を単独実行にすることは維持すべきです。既に凍結ビルドと結果再利用もあります（`MEASURE.md:9,43`）。待ち時間を測らず分散基盤を作る方が非効率です。
- **資産パイプラインは「ない」わけではない。** `Setup/Import-*.py`、`Refresh-AC01Body.*`、出典記録があります。次の改善は新ツール導入より、サイズ・軸・当たり・LOD・アニメ・再取込みの合格条件をモデルごとに揃えることです。

## 3．良い点・変えない方がよい点

業界平均より優れていると定量比較はできませんが、以下は明確な強みです。

- 凍結ビルド、manifest、機械情報、結果再利用を備えている。
- プロセス終了だけでなく、専用の失敗数で判定する。
- UnitIDと表示の分離、保存検査、失敗時の扱いを重視している。
- 失敗した仮説・無効な比較・ユーザー判断を残している。
- Eの性能基準とH/I/Jの地形差を分けている。
- 契約修理を勝率で採否判断しない規則を導入した。

他ゲームから取り入れるなら、数値やアーキテクチャのコピーより次です。

- **操作負担を減らす：** Disintegrationの開発者インタビューは、RTSからFPSと戦術操作の組合せへ設計を絞った経緯を示しています。ただしNS2やNuclear Dawnの評判まで同じ資料で立証はできません。FutureBattleでは「FPS中に指揮へ戻りたくなった理由」を試遊で記録するのが具体的です。[開発者インタビュー](https://www.unrealengine.com/developer-interviews/disintegration-blends-fps-and-rts-to-create-a-more-tactical-shooter)
- **意図を読めるようにする：** 掛け声を大量追加する前に、選択部隊へ「補給中／経路待ち／保持」を表示する。引用記事は行動の事前フィードバックを支持していますが、提示されたF.E.A.R.・Haloの逸話全部の直接根拠ではありません。[行動のフィードバックに関する記事](https://www.gamedeveloper.com/design/7-ways-to-make-your-ai-smarter)
- **詳細度を分ける：** ALiVEの仮想化は実体の生成・非生成を扱う仕組みです。FutureBattleの「区画ごとの判断頻度」と方向は近くても同じ方式ではありません。既存のUnitID分離を活かし、まず判断予算の段階化に留めるのが適切です。[ALiVE公式資料](https://www.alivemod.com/alive3/sys_profile_spawner.htm)

## 5．追加4案への回答

- **(i) 通し手順と固定場面を評価道具より前に：修正して賛成。** 手順と検証条件を先に決める。ただし固定場面を多数完成させるまでN5を止めず、最初の一場面と解析改善を並行にする。
- **(ii) 新切替に2週間の期限：見直し期限なら賛成。** 2週間で強制採否・自動削除はしない。未発動、計測待ち、依存修理待ちは「休止と再開条件」を決める。恒久設定や診断引数には同じ期限を課さない。
- **(iii) 固定刻みは依存調査だけ先に一件：強く賛成。** 今回のコードだけでも調査の価値は明確。10Hz化や全面リプレイ対応まで抱え込まない。
- **(iv) 数値試験の再開前に相性表一枚：賛成。** ただし「期待する役割を確かめる表」にし、机上の費用対効果を唯一の正解にしない。

既に決めた実装順は維持できます。先頭を**「試遊と小場面で問うことを決める＋必要最小限の解析」**に少し具体化すれば、移動修理と守備配置を遅らせず、以後の試験の無駄を減らせます。
