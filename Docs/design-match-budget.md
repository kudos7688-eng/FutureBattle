# 調査試合の回数を減らす（実態の集計と案）

2026-11-25 11時 Claude（系統「試合数の統制」、掲示板 C26）。**検討と案だけ。決まり（AGENTS.md・MEASURE.md）と共用スクリプトは変えていない。採否はユーザー判断。** ビルドも試合も実行していない。Codex に記録の調査と案への意見を頼み、数字は Claude が manifest とロックの履歴から数えた。

依頼（ユーザー、11-25）：「各セッションが調査のたびに調査項目を足して、それぞれ複数の調査試合を回している。ある程度統制して回数を減らせないか」

## 0. 結論（先に）

1. 11-22 0時〜11-25 11時（約3.4日）に **試合 1,476本・ロックの保持 190回（計53時間）・待ちの合計 235時間**（待ちの中央値59分）。
2. **待ちを決めているのは試合の本数ではなく「回」の数**。1回＝ビルド＋回帰試験＋試合1バッチで中央値13分。試合は並列なので、2本でも12本でも1バッチは約9分。本数だけ減らしても待ちはあまり減らない。
3. 試合の **約2割（298本）は、すでにある試合と結果が完全に同じ**だった（基準の取り直し、記録だけ足した回し直し、切替を入れても何も変わらなかった試合）。

## 4. 案

### 案A 段階の順と、試合の前の申請1行（決まりの追加）

- 順番：**① 固定場面（1〜2分）で成立 → ② 1試合で発動回数（`Analyze-MatchDelta.py` の `ACTIVATIONS`）→ ③ 既存の2シードで基準との差 → ④ 採用の候補だけ 239・277**。②で発動0回なら③へ進まず、条件（前提の切替・マップ）を直すか、「通常の試合では起きない」と書いて止める。①に使える固定場面が無いときは、試合を増やす前に固定場面を作る。
- 申請：③以上を回す前に、掲示板へ1行（`Board.py note` に種別を足すか、`Docs/experiments.md` の行）。**問い／既存の結果で答えられない理由／条件の数×シード／やめる条件**。書く前に `Board.py find` で同じ切替・同じマップの結果を引く。
- 費用：決まりの文と、掲示板の種別1つ（小）。eval-playtest の `test-map.md`・`experiments.md`・`Analyze-MatchDelta.py` をそのまま使う（新しい道具は作らない）。
- 効果：(c)(d) と「切替が違うのに結果が同じ」193本の一部。**−100〜200本（7〜14%）、−10〜15回**。
- 難点：②は1回ぶんロックを使う（③と同じ回にまとめられないと回が増える）。対策は「②と③を同じ保持の中で続けて行い、②が0なら③を流さず手放す」。

### 案B 基準の台帳（共用の基準試合）

- main の既定で、決まったマップ・シード（案：**I・J・K × 7・43、H × 7 の7本**。評価は H/I/J、マップK は弾薬・マップ系統が使う）を、**既定が変わった直後に1回だけ**回し、結果フォルダの名前・凍結ビルド・commit・`metrics` の指紋を `FPS\.lock\baselines.json`（作業ツリーの外）に置く。全系統はそこから引く。
- 系統の作業ツリーの DLL は main と違うので、今の再利用の鍵（DLL・マップ・Config・引数のハッシュ。`Test-WideSight.ps1:191–207`）では写せない。**同等の登録**を別に持つ：切替 OFF の1本（マップI seed 7）が台帳の指紋と一致したら、その DLL を「基準と同等」と登録し、残りは台帳を**参照**する（写して自分の実測と書かない）。
- Codex の注意：1マップ1シードの一致は残り全部の同等の証明ではない。だから同等の登録は「既定0の切替だけを足した差分」に限り、既定の経路に触れた差分・Config を変えた差分は全部の基準を回す。鍵には Engine の版・Content 全体・解析の版が入っていないので、台帳には commit と凍結ビルドの名前を必ず持つ。
- 費用：台帳のファイルと、`Analyze-MatchDelta.py` が台帳の名前を受け取る入口（eval-playtest の範囲。半日）。持ち主を1つ決める。
- 効果：(a) の 86本と (e) の一部。**−50〜90本（3〜6%）**。回はほとんど減らない（基準は試験と同じバッチで流れていた）。副次の効果として、全系統が同じ基準と比べるので結果どうしを並べられる。
- 難点：既定が7時間に1回変わる今のままでは、台帳がすぐ古くなる → 案E と組にする。

### 案C 標準の記録（回し直さなくて済むように）

- 今の記録：`-BattleStateTrace=N` は N フレームごとの CRC で値は戻せない。`-BattleStateTraceDetail` は兵ごとの位置・HP・弾・遮蔽・標的（小隊の命令は無い）。`-BattleShotLog` は射撃ごと。`-BattleFireTimeLog` は追加の探索をするので常用に向かない。保存（BattleSave）は時点の写しで履歴が無く、リプレイ（FieldReplay）は位置と表示が中心。**後から命令の理由を取り出す方法は今は無い**（Codex、`BattleStateTrace.cpp:44–93`、`BattleFieldReplay.cpp:41–44`）。
- 案：**小隊ごとに5秒に1行**（小隊ID・位置・命令と任務・区画・人数・弾の割合・補給の状態・詰まりの有無・交戦中か・目標）を、計測の起動では常に出す。読むだけで、探索や光線を足さない。
- 見積り（Codex の推定、未計測）：40〜80小隊で 7,200〜14,400行・約2〜7MB（今の `run.log` 18MB の 12〜40%増）。負荷は毎秒8〜16行の書き出しで、ms は測っていない。乱数は使わないが、入れる前後で `IDENTICAL` の確認が要る（1回）。
- 費用：C++ 1日＋一致の確認1回。`run.log` は期間で 20GB あるので、2日より古いものを `Move-OldRuns` の対象にするか圧縮する。
- 効果：(b) の 26回・107本のうち、位置・命令・補給・詰まりで答えられた分。**−10〜15回（2〜3時間）、−40〜60本**。先に取っておけない問い（殴れない理由など）は残る。
- 合わせて：**記録だけを足したビルドは、試合を回し直す前に `Compare-MatchResults.py` の1本だけ**（結果が同じと分かれば、残りのシードは前の結果＋新しい記録の1本で読む）。決まりの1行で済む。

### 案D ロックを「排他」と「相乗り」に分ける（待ちに一番効く）

- 今は、ビルドも試合も取り込みも1つの列。凍結ビルドの写しから起動する試合は、ほかのビルドや Config の編集の影響を受けず（`MEASURE.md` 0-3）、30FPS 固定刻みの結果は並列の数に左右されない（同 1章）。実際に、裏で流した総当たりが他の保持と重なった試合が既に100本以上あり、合格している。
- 案：**排他の列**＝描画あり・性能の計測、main のビルドと取り込み、マップの生成。**相乗りの枠**＝凍結ビルドからの描画なしの試合（全体で12本まで、系統をまたいで詰める）と、作業ツリーのビルド（同時に1つ）。`Lock-Queue.ps1` には `-Share` の印が既にある（`Docs/design-lock-queue.md` 4章の案）。
- 効果（概算、未検証）：保持 53時間のうち試合の 35時間が重ねられ、並列の平均 5.6本 → 10本前後なら約20時間。使用率 66% → 40%台で、**待ちの中央値 59分 → 10〜20分**。
- 費用：`Lock-Queue.ps1` に枠の数え方を足す（半日）＋**負荷をかけた状態での一致の確認**（ビルド中に流した試合と単独の試合が `IDENTICAL` か。2〜4本、1回）。
- 難点：時間の値は比べられなくなる（今も並列の試合は `timingComparable=false`）。`Test-Battle` など時間切れのある試験がビルドと重なって落ちる恐れ → 回帰試験は自分のビルドの直後に排他で行う形を残す。作業ツリーから直接起動する試合（今 45%）は相乗りできないので、**比較に使う試合は凍結ビルドから**に揃える（凍結は約5秒・約200MB。古い凍結ビルドの片付けが要る）。

### 案E 既定の切替と main への取り込みを定時にまとめる

- 既定を変えるコミットと、系統の main への取り込みを **1日2回の定時**（案：6時と18時）に集める。1回のビルド＋回帰で複数の取り込みを済ませ、直後に案B の基準7本を1バッチ（約10分）で取り直す。
- 効果：(e) の取り直しが定時の1回になる。試合なしの保持 38回・6.7時間 → **−2〜3時間**。台帳が半日は古くならない。
- 難点：取り込みが最大12時間遅れる。ユーザーが試遊で要るものは `-Urgent` で定時の外に入れる。複数の取り込みをまとめると、回帰が落ちたときにどれが原因か切り分けが要る。
- **夜間の一括実行は、今は効かない**：保持は24時間平らで、夜に空きが無い（むしろ0〜10時が多い）。時間帯を移すだけでは本数も時間も減らない（Codex も同じ意見）。定時にまとめる価値があるのは基準と採用の確認（④）だけ。

### 案F 枠（上限）

- **1つの問いあたり**：発動の確認1回＋比較1回（8本まで）で一度 STATUS に書く。続けるなら申請の行を書き直す（何が分かって、何を足すか）。
- **1系統あたり**：1日6回（今の多い系統は7回前後）。超えたら禁止ではなく、列の中で「今日の回数が少ない系統を先にする」（`Lock-Queue.ps1` の並べ方。案D を入れるなら不要になる可能性が高い）。
- 総当たり（`Run-EconomyMatrix` で16本以上）は、申請の行に条件の表を書いてから。
- 難点：数字に根拠は薄い（今の実績の少し下に置いただけ）。枠は「細かい回を1回にまとめる」圧力として効かせるもので、調べること自体を止めない。

### 相乗り（1つの試合に複数の系統の切替を入れる）について

- **できる**：読むだけの記録どうし、記録＋1つの試験切替。
- **してはいけない**：挙動を変える切替を2つ。片側の切替（`-BattleAreaTrialTeam`・`-BattleArmsTeam`）は入れる側を絞るだけで、相手・資源・拠点を通じて互いに影響する。場所が離れていても同じ。A+B の結果は A だけ・B だけに分けられない（Codex、`BattleArms.cpp:60`、`BattleTactics.cpp:135`）。組み合わせを見たいときだけ使う。

## 5. 標準的なやり方との比較（Codex の意見）

| 標準のやり方 | ここでは |
|---|---|
| CI の段階分け（投入前は速い試験、取り込み後は広い試験、夜間は重い試験） | 合う。投入前＝固定場面と発動の確認、取り込み後＝共用の基準、定時＝採用の確認（案A・B・E） |
| 入力のハッシュによる結果のキャッシュ（Bazel 型） | 完全に同じ入力に限れば合う（今の再利用）。DLL が違う「意味として同じ」は別の制度にして、証拠と失効の条件を持つ（案B） |

### 8.1 ロックの分け方（案D の具体形）

- **作業の列（今までの列。1つずつ）**：ビルド、回帰試験、main への取り込み、マップの生成、描画あり・性能の計測。呼び方は今までと同じ（`-Join` → `-Wait` → `-Release`）。
- **試合の枠（新しい。全体で12本まで、系統をまたいで同時）**：凍結ビルドから起動する描画なし・30FPS の試合だけ。`-Join -Matches <本数>` で入り、空きがあればすぐ始まる。作業の列の持ち主がいても並んで流れる。
- **単独**：性能・描画ありの計測は `-Join -Alone`。試合の枠が空になるまで待ち、持っている間は試合の枠も始まらない。
- 1回の典型：作業の列で「ビルド＋回帰試験＋凍結」（5〜7分）→ `-Release -Matches <本数>` で作業の列を手放し、そのまま試合の枠へ移る → 試合（約9分）→ `-Release`。次の系統のビルドは、前の系統の試合と重なって進む。
- 前提の確認（変える前に1回）：(1) ビルド中・他の試合と同時に流した凍結ビルドの試合が、単独のときと `IDENTICAL`。(2) 回帰試験 `Test-Battle` が、試合の枠が埋まった状態でも `failures=0`。**(1) が崩れたら変えない。(2) が崩れたら、回帰試験は `-Alone` で行う形にするか、変えずにユーザーへ報告する**。
- 互換：今ある列（`queue.json`）の形と引数は変えない。試合の枠は別のファイル（`matches.json`）に持つ。変更の前から待っている古い `-Wait` は列のファイルを古い形で書き戻すので、列のファイルには新しい欄を足さない。

### 8.1b 前提の確認の結果と、Codex のレビュー（11-25 12時）

- **前提の確認（11-25 11時38分〜12時11分、凍結ビルド `joinfight1-111753`、30FPS・描画なし）**
  - 単独の4試合（マップI・K × シード7・43、`idchk-alone-*`）と、同じ4試合を「埋め草8試合（計12本）＋ `FutureBattle-budget` の初回の全ビルド＋ `Test-Battle`」と重ねたもの（`idchk-load-*`）を `Compare-MatchResults.py` で比べ、**4組とも `IDENTICAL`**（時間を除く78項目）。実時間は1試合 310〜347秒 → 506〜548秒（約1.6倍）。埋め草8本も合格。全ビルドは741秒で成功。
